## Sign/usage conventions CONTRIBUTING.md's table doesn't cover

`CONTRIBUTING.md#sign-conventions` covers 9 controllers. Two more with non-obvious `compute()` semantics:

| Controller | Convention |
|---|---|
| `GeneralizedPredictiveControl` (GPC) | Prefer `computeRef(y, r)` over `compute(error)` - the CARIMA reference filter needs `y` independently, not just the error. |
| `ExtremumSeeker` (ESC) | `compute(J)` expects the cost **evaluated at the current dithered operating point**, not at a separate estimate - feeding `J` from the wrong point breaks the demodulation silently (no exception, just wrong convergence). |

## Verified safety-critical caveats

- **`DiscreteMPC`/`GeneralizedPredictiveController`: never call `ldlt_.compute()` from outside
  `buildCondensedMatrices()`** *(verified, `lib/DiscreteMPC.h:191-193`)* - doing so with a stale/incorrect
  matrix silently corrupts every subsequent QP solve. No exception, no warning.
- **`DiscreteMPC`/`GeneralizedPredictiveController` are NOT safe with `AtomicParamBuffer`**
  *(verified, `docs/deployment.md:319-334`)* - their `setParams()`/`setPlant()` rebuild large Eigen
  matrices (`H_`, `Phi_`, `ldlt_`) via multiple heap allocations and factorisations; this is not atomic or
  trivially copyable. Calling it from a background thread while the RT thread is inside `computeRef()` is
  a genuine data race that corrupts those matrices with **no warning** - wrong control outputs, not a
  crash. Safe patterns: pause the RT loop during the update, or double-buffer the whole controller object.
  Scalar-param controllers (`DiscretePID`, `DiscreteLeadLag`, `DiscreteSMC`, `DiscreteADRC`) are fine with
  `AtomicParamBuffer` since their params are POD structs.
- **`AntiWindupWrapper` wrapping a `DiscretePID` with `Kb != 0` throws at construction**
  *(verified, `lib/AntiWindupWrapper.h:85-89`)* - this is an enforced runtime check, not just documented
  advice. (Earlier drafts of this kind of note tend to undersell it as "remember not to do this"; it's
  actually guarded.)
- **Discrete integrator stability:** `Ki * Ts < 2 * Kp` for `DiscretePID` (`docs/deployment.md:21`);
  **Nyquist limit** `Ts < pi / continuousPole` for `DiscreteLeadLag` (`docs/deployment.md:37`); **ADRC ESO**
  `omega_o * Ts < 0.5` strictly, recommend `<= 0.4` for margin (`docs/deployment.md:188`, also in
  `CONTRIBUTING.md`). All three are hard math constraints, not tuning suggestions - violating them
  destabilises the loop or grows ESO state unboundedly.
- **`DiscreteLQR::dareConverged()` must be checked before using the gain** (`docs/deployment.md:48-49`) -
  an unconverged DARE result can be unstable; causes are an unstabilisable plant, near-singular `R`, or
  non-PSD `Q`.
- **All scalar `IController`s hold their last valid output on NaN/Inf input** (`docs/deployment.md:511-516`)
  - they fail silently-safe rather than propagating garbage, but that means a sensor fault shows up as a
  "frozen" output, not an exception. Validate upstream if you need to detect the fault itself.

## Non-obvious per-class behavior (not in CONTRIBUTING.md)

| Class | Caveat |
|---|---|
| `DiscreteLQG` | `compute()` takes the **raw plant output `y`**, not error (unlike most `IController`s). Internally, the Kalman update uses the *previous* `u[k-1]` for the `D*u` feedthrough term - accuracy degrades on plants with `D != 0`. |
| `DiscreteHinf` | Mixed-sensitivity synthesis helpers are SISO-only. Feasibility requires `spectralRadius < gamma^2`; nonzero `D22` in the generalized plant degrades synthesis quality. |
| `ExtendedKalmanFilter` | Internal `f_` should be well-conditioned; on stiff plants (fast electrical/hydraulic time constants) a single forward-Euler step loses accuracy - sub-step with RK4 internally if needed. |
| `UnscentedKalmanFilter` | For state dimension `n >= 4`, the default `alpha = 1e-3` drives `Wc0` toward 0/negative, amplifying noise; raise `alpha` toward 0.1-1.0. Additive-noise model only (no multiplicative/state-dependent noise - augment the state if you need that). |
| `GaussianProcess` | `predict()` throws if `fit()` hasn't been called since the last data addition. Fixed-budget mode evicts oldest points once `n_max` is reached. |
| `EchoStateNetwork` | `reset()` clears reservoir state only - **not** `W_out` or training data (intentional, supports warm-started online learning; don't expect a fresh model after `reset()`). |
| `SmithPredictor` | `delayModel` must be the **delay-free** plant `P0(z)`; the wrapper adds the delay back internally. Passing the full delay-included model double-counts the delay. Even a 1-sample delay mismatch can destabilise a lightly damped plant. |
| `ControllerStack` (Supervisory) | Needs at least one entry that's always eligible/healthy as a fallback - if none qualifies, output just holds with a warning, it doesn't fail loudly. |
| `GainScheduledController` (LinearBlend) | Advances the internal state of **both** bracketing controllers every step (not just the active one) - inactive integrators can wind up. Use `NearestNeighbor` if you need hard switching instead. |
| `SubspaceID` / `SINDy` | Need persistent excitation - input must cover at least as many frequencies as the assumed model order, or identification silently returns garbage rather than failing. |

## Case-study patterns worth knowing before writing a new one

- **Negative-static-gain plants are a recurring, intentional pattern**, not a bug to "fix": Aircraft Engine
  Thermal Management (more flow -> lower outlet temp), Bouyancy-Driven Airship (more actuator input ->
  less pitch), Solar Cooker (more shade -> less solar -> lower pot temp). If you're adapting an MRAC-style
  controller to one of these, the adaptation gains (`gamma_r`, `gamma_y`) typically need to be **negative**
  to match - positive gains drive the parameter estimate the wrong way and the output clamps to a rail.
- **TLCS-style mode switching needs `bumplessInit()` called every step**, not just at the switch instant
  (Buck-Boost converter pattern) - otherwise the inactive controller's integrator doesn't track the active
  one and you get a transient on switchover.
- **`FuzzyPID`/`FuzzyPD` inner bounds should be loose (`[-1, 1]`), not `[0, 1]`** - seen in both the Buck-Boost
  converter and the Active Suspension 6x6 EV study; tight `[0,1]` bounds suppress overshoot correction.
- **Not every case study uses `lib/DiscreteSMC`** even when its README says "SMC" - Tug Boat Numerical
  Simulation hand-rolls the paper's own sliding-surface equations (integral-type, not derivative-gain)
  because the source paper's formulation doesn't match the library class. Check the study's own
  `controllers.{h,cpp}` before assuming it's a thin wrapper over a `lib/` class.
- `tools/new_case_study.py`'s placeholder plant/controller actually runs and writes real-looking CSVs -
  `tools/case_study_tracker.py`'s "Open placeholder" status (matched against the scaffold's literal
  template body) is the only reliable signal that a study hasn't really been started, not the presence of
  `logs/*.csv`.
