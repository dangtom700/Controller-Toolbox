6// SimPlant - discrete-time plant simulator shared by SimSensor and SimActuator.
7//
8// Owns the state-space model and its current state vector. Both simulation
9// adapters hold a reference to the same SimPlant instance so that sensor
10// readings and actuator commands remain consistent within one sample step.
11//
12// Typical closed-loop simulation pattern (one step k):
13//
14// double y = sensor.read(); // 1. read current output y[k]
15// double u = controller.compute(r - y); // 2. compute control action
16// actuator.write(u); // 3. write u[k] -> advances plant to x[k+1]
17//
18// The step order matters: read() must be called BEFORE write() in the same
19// sample because write() advances the state. If the step order is reversed
20// the simulation models a one-step computational delay (which is also valid
21// for hardware - just document the convention and stick to it).
22//
23// Thread safety: step(), setState(), reset(), and output() are all protected
24// by an internal std::mutex and are safe to call from separate threads.
25// This enables Hardware-in-the-Loop (HIL) setups where the plant runs in a
26// background thread while a logger or visualiser reads output() concurrently.
27// Note: each call acquires the mutex independently - a read-then-step sequence
28// is NOT atomic without an external lock. For simulation-only use from a
29// single thread the mutex overhead is negligible.
